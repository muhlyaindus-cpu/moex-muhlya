# Trading Lab File Matrix

Цель: зафиксировать, чем пользуемся регулярно, что держим как опцию, и что не должно попадать в боевой контур напрямую.

## Использование по умолчанию

- KEEP (рабочий минимум):
  - `README.md` — входная точка и команды запуска.
  - `moex_iss_download.py` — загрузка исторических данных MOEX ISS.
  - `features.py` — базовые фичи для бэктеста.
  - `policy_defaults.py` — единые дефолты политики.
  - `rsi_backtest.py` — быстрый офлайн-бэктест логики.
  - `validate_policy.py` — gate-проверка до допуска в paper/live.
  - `export_policy.py` — экспорт `policy.json` для Go-контура.
  - `artifacts/validation_report.json` и `artifacts/validation.passed` — артефакты качества.

- OPTIONAL (использовать по задаче):
  - `train_ppo.py` — только если реально тренируем новую модель.
  - `env.py` — учебная Gym-среда, не обязательна для ежедневной валидации.
  - `RL_PLAN_D3QN_PER_MOEX.md` — roadmap, не операционный файл.

- DATA (технические артефакты):
  - `data/_smoke_prices.csv` — smoke-набор, не источник для продуктовых выводов.

## Почему "полигон" иногда не используется

- В рабочие сессии фокус часто смещается на эксплуатацию VPS/Finam (reject, лимиты, сессия MOEX).
- Когда рынок закрыт, оперативно важнее стабильность контура, чем переобучение.
- Лаборатория должна запускаться осознанно под конкретную гипотезу, иначе это шум.

## Мини-ритуал перед обновлением боевой политики

1. Сформировать/обновить датасет через `moex_iss_download.py`.
2. Прогнать `validate_policy.py` на train/test split.
3. Проверить артефакты: `validation_report.json` и `validation.passed`.
4. Только после этого переносить `policy.json` в путь `AGENT_POLICY_PATH`.
5. Первым этапом проверять в `paper`, затем в live малыми объёмами.

## Жёсткое правило

Ни один Python-скрипт из `trading-lab` не должен исполнять сделки в боевом контуре напрямую.  
Боевой execution и риск-контур остаются в Go.
