# Зачем Мие «стакан» (и что именно мы берём)

## Задача для Мии

Мия — **наблюдатель**, не исполнитель сделок. Свечи дают **направление и импульс** за окно времени. **Лучшие цены и видимая глубина** (если биржа их отдаёт) дают **микроструктурный контекст**:

- насколько **широк спред** между лучшим bid и ask (ликвидность «на кассе»);
- есть ли **дисбаланс** по глубине bid vs ask там, где колонки `BIDDEPTH` / `OFFERDEPTH` заполнены;
- согласованность с **LAST** (нет ли странных разрывов — как сигнал «проверить данные»).

Это помогает:

- не переоценивать «bullish/bearish» по свечам, когда **спред раздут** или **книга пустая по глубине**;
- в отчётах отдельно помечать **риск плохого исполнения** для Мухли (как подсказка, не как приказ).

## Откуда данные

### Московская биржа (MOEX ISS) — реализовано в `miya-online-watch.sh`

Используется публичный снимок **`marketdata`** по режиму **TQBR** (лучший bid/ask, last, при наличии — глубины).

Важно: **полный многоуровневый стакан** через ISS (`orderbook`) у MOEX часто доступен **только подписчикам**. Поэтому в скрипте зафиксировано примечание `scope=best_bid_offer_last_depth`: мы сознательно берём **то, что стабильно доступно без подписки**, а не обещаем «весь стакан».

### Finam — пока не подключали

Технически возможно через **торговый API Finam** (те же учётные данные, что у Мухли), но это:

- отдельный контур **авторизации** и лимитов;
- другая семантика идентификаторов инструмента;
- риск смешать **рыночные данные** и **торговый контур**.

Разумный порядок: **сначала MOEX ISS (без секретов)**, затем — по необходимости — опциональный модуль «Finam depth» за флагом и отдельным дизайном.

## Артефакты

- `online_orderbook_latest.md` / `online_orderbook_latest.json` — снимок;
- ключи `ORDERBOOK_*` в `miya_online_signal.env` — для Мухли/отчётов (мягкое использование, fail-safe).
